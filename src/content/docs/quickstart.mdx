StackBlaze is a deployment platform. You provision infrastructure on a **project canvas**, develop against that infrastructure, and deploy from Git, a Docker image, the CLI, or a template.

This guide covers two ways to get going:

1. **Deploying your project** — bring your code.
   - [From GitHub](#deploying-your-project--from-github)
   - [With the CLI](#deploying-your-project--with-the-cli)
   - [From a Docker image](#deploying-your-project--from-a-docker-image)
2. **Deploying a template** — pre-wired software from the catalog.

## Deploying your project — from GitHub

1. Open [the dashboard](https://dashboard.stackblaze.cloud) → **New project**. Give it a name (or leave it blank to auto-generate one), pick a region, and click **Create Project**.
2. On the empty canvas, choose **GitHub repository** (or **+ Service → Git repository**). Link GitHub if prompted, then pick the repo and branch.
3. The service is **staged** on the canvas. Click **Commit 1 change** in the toolbar, review the change, and click **Deploy 1 change**.

StackBlaze clones the commit, builds it (your `Dockerfile` if there is one, otherwise Railpack), and rolls the service out. A public service gets a `*.stackblaze.app` URL; you can add a [custom domain](/networking/custom-domains/) later.

If the build fails, open **Logs** on the service and scroll the full build log — the useful error is often not the last line.

## Deploying your project — with the CLI

Install, then from your app directory:

```bash
curl -fsSL https://stackblaze.com/install.sh | sh
stackblaze login
stackblaze init
stackblaze up
```

`init` creates a project and links this folder to it. `up` creates the service from the repo's git remote and current branch (push your commits first) and streams the build. A folder with no git remote (or `up --local`) is uploaded instead. Then:

```bash
stackblaze open
```

That opens the service in the dashboard (`--app-url` opens the app itself). To ship later commits, push them and run `stackblaze up` again: it updates the existing service and rebuilds. See [CLI](/cli/).

## Deploying your project — from a Docker image

1. **New project**, then open the empty canvas.
2. **+ Service → Docker images** (or **Docker image** on the empty canvas).
3. Search for an image or paste one such as `ghcr.io/org/app:tag`. Use the full registry URL for anything that is not Docker Hub.
4. **Commit** the staged change, review it, and **Deploy**.

The process must listen on `PORT`. Private registries need credentials on the service.

## The canvas

GitHub, CLI, Docker, and templates all end on the same **project canvas**. This is mission control: services, databases, environments, variables, and [staged changes](/deploy/staged-changes/).

Click a tile for its code, deployments, variables, logs, metrics, and settings. **+ Service** adds templates, a Git repository, Docker images, databases, add-ons, or an import (Compose / `render.yaml` / `fly.toml`).

## Deploying a template

1. **+ Service → Templates** on a canvas (or **Template** on an empty canvas).
2. Search the [catalog](https://stackblaze.com/templates).
3. Fill in any prompted values.
4. **Commit** the staged changes, review them, and **Deploy**.

The canvas provisions every service and database the template defines.
