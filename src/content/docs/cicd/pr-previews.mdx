Each pull request can get its own [environment](/deploy/environments/) named `pr-<number>`. It is a copy of the environment that deploys the PR's target branch, so you can try the change before you merge.

The preview is deleted when the PR is merged or closed, or after a number of days without a push.

<Diagram file="pr-previews.svg" alt="Diagram of isolated PR preview with web, Postgres, and Redis services" />

## Turn previews on

Open **Project settings → General → Preview environments** and turn on **Create previews for pull requests**. Click **Save changes**.

Previews need the StackBlaze GitHub App, so StackBlaze can see pull requests. Your plan must include preview environments.

## Which pull requests get a preview

Under **Settings → When**:

- **Pull requests**: **Every pull request** (default) or **Only when asked for**.
  - Every pull request: skip one with the `no-preview` label or `[skip preview]` in the PR title.
  - Only when asked for: add the `preview` label or put `[preview]` in the title. Removing the label deletes the preview.
- **Bot pull requests**: off by default. Turn on to give Dependabot, Renovate and other bot PRs a preview.
- **Delete after**: 1 to 30 days without a push (default 7). A preview is also deleted when its PR is merged or closed.

Pull requests from forks never get a preview, because their code would run with your project's variables and databases.

## What a preview contains

- The base environment is the one whose services on the PR's repository deploy from the PR's base branch. Production wins when several match.
- Services on the PR's repository follow the PR's head commit. Services the PR does not change reuse the base image instead of building.
- Under **Settings → What → Apps**, uncheck services to leave them out (for example a worker).

## URL and PR comment

Each web service in the preview gets its own generated URL. StackBlaze posts one comment on the pull request and updates it in place: it lists each preview URL as building, then ready or failed, and marks the rows removed when the preview is deleted.

The project canvas also shows previews in the environment switcher.

## Data in previews

Databases in a preview **start empty**. They are separate from the base environment. To copy data in, open the preview on the canvas, click **Sync from** *base* in the preview bar and check **Data** (databases and volumes). Check **Configuration** to also copy variables, settings, and apps. Previews are never backed up.

## Advanced: seeds and variables

Under **Advanced**:

- **Seed commands**: run once in each new preview after its apps start, for example `npm run seed`. A seed runs with that app's image and variables. Up to 10.
- **Variables**: previews copy every variable as-is. For each variable, pick **Don't copy** or **Use this value** (for example a test Stripe key). A rule can apply to one app or **All apps**. Rules apply to new previews and to Sync.

`previewValue` in [`stackblaze.yaml`](/blueprint/) is accepted but ignored: set preview values here instead.

## Updates and promotion

Every push to the PR branch rebuilds the preview's services whose watched paths changed ([build filters](/cicd/auto-deploy/#build-filters) apply). The URL stays the same.

To ship a preview, pick **Promote** from its row's menu on the **Deployment** tab. A Git service rebuilds the base environment at the preview's commit; a Docker image service rolls the base onto the preview's image tag. The production hostname stays the same.

## Step by step

1. **Turn previews on** in **Project settings → General → Preview environments**.
2. **Open a pull request** against the branch your environment deploys.
3. **Open the preview URL** from the PR comment, or switch to the `pr-<number>` environment on the canvas.
4. **Push more commits**. The preview rebuilds in place.
5. **Merge or close the PR**. StackBlaze deletes the preview: its services, databases, and volumes.
