Every deploy is kept on the service's **Deployment** tab. When a new deploy causes problems, roll back to one that ran before. There is no rebuild: StackBlaze rolls out the image that deploy already built.

<Diagram file="rollback-revisions.svg" alt="Deployment history of immutable image tags. Pick a prior revision to re-roll the same image with no rebuild. Database migrations are not undone." />

There are two kinds of rollback:

| Action | What it restores | What stays as it is now |
| --- | --- | --- |
| **Instant Rollback** | That deploy's image **and** the variables and settings it ran with | Add-ons, volumes, domains, and your plan |
| **Rollback Config** | Only the configuration of an earlier config release, applied as a new save | The running image, add-ons, volumes, and domains |

**Instant Rollback turns auto-deploy off**, so the next push does not undo it. Turn **Autodeploy** back on in **Settings** when you are ready.

:::caution[Database migrations are not rolled back]
Rolling back your application code does not undo database schema changes. Design migrations to be backward-compatible (additive-only) so the previous version can run against the new schema.
:::

## Which deploys you can roll back to

- **Instant Rollback** is offered in the **production** environment, on deploys that went live and were later replaced. It is not offered on the deploy that is live now, on failed or canceled attempts, or in PR previews.
- **Rollback Config** is offered on earlier deploys linked to a saved configuration that differs from the live one.
- **Redeploy** is offered on any row. For a Git service it rebuilds and deploys that row's commit.

## Rollback from the API

```bash title="terminal"
export STACKBLAZE_TOKEN=sb_pat_…

# Instant rollback: image + configuration of a past deploy
curl -sS -X POST \
  https://api.stackblaze.cloud/api/deployments/rollback-deploy/acme-app/production/api/DEPLOYMENT_ID \
  -H "Authorization: Bearer $STACKBLAZE_TOKEN"

# Configuration only: preview, then apply a stored config release
curl -sS https://api.stackblaze.cloud/api/deployments/rollback/acme-app/production/api/REVISION_ID \
  -H "Authorization: Bearer $STACKBLAZE_TOKEN"
curl -sS -X POST \
  https://api.stackblaze.cloud/api/deployments/rollback/acme-app/production/api/REVISION_ID \
  -H "Authorization: Bearer $STACKBLAZE_TOKEN"
```

List deploys (with their IDs) with `GET /api/deployments/{pipeline}/{phase}/{app}`. Rolling back needs `app:write`.

## Step by step

1. **Open the Deployment tab**

   Open the service on the canvas and go to **Deployment**. Deploys are listed newest first with their commit or image tag, message, and state.

2. **Inspect the deploy you want**

   Open a row's menu and pick **Inspect Deployment** to see its logs before you roll back.

3. **Roll back**

   From the row's menu, pick **Instant Rollback** and confirm, or pick **Rollback Config**, review the changes, add an optional message, and click **Rollback**.

4. **Verify**

   The rollback shows as a new row on the **Deployment** tab. The deploy that caused the issue stays in the list.
