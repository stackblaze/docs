A Git-connected service [auto-deploys](/deploy/github/) on every push to its branch. You can turn this off per service, skip one commit, or limit which changed files trigger a build.

<Diagram file="deploy-lifecycle.svg" alt="Deploy lifecycle from GitHub push through build and Kubernetes rollout to a live stackblaze.app URL" />

## Deploy pipeline

`git push` → GitHub App webhook → Build (image) → Pre-deploy command (if set) → Rollout → Live

Each attempt shows on the service's **Deployment** tab with its state: queued, building, pre-deploying, rolling out, live, then superseded when a newer deploy goes live. Failed and canceled attempts stay in the list.

## Deploy settings

Open the service, then **Settings**. These sit with the repository and build method.

- **Autodeploy**: deploy when you push to the connected branch. On by default.
- **Branch**: the branch this service deploys. Pushes to other branches are ignored. The name must match exactly.
- **Build filters**: which changed files trigger a build. Set them in [`stackblaze.yaml`](/blueprint/) as `buildFilter.includedPaths` and `buildFilter.ignoredPaths` (gitignore-style globs, up to 50 each). See [Build filters](#build-filters).

:::note
Push events come from the StackBlaze GitHub App and are verified before a build starts. StackBlaze does not add a webhook to each repository. While a build runs, StackBlaze posts a check run on the commit in GitHub.
:::

## Skip a deploy

Put one of these anywhere in the commit message: `[skip deploy]`, `[deploy skip]`, `[skip cd]`, or `[cd skip]` (any case). Nothing builds, the current deploy keeps running, and the skipped push shows on the **Deployment** tab.

`[skip ci]` does **not** skip a StackBlaze deploy.

## Build filters

- With no filters, a service whose build path is the repo root rebuilds on any change.
- A service with a build path such as `apps/api` only rebuilds when files under `apps/api/` change. This is the default; you do not have to configure it.
- `includedPaths` replaces that default with your own list.
- `ignoredPaths` wins: a push where every changed file is ignored does not rebuild.
- When GitHub does not report the changed files (for example a force push), the service rebuilds.

```yaml title="stackblaze.yaml"
services:
  - name: api
    rootDir: apps/api
    buildFilter:
      includedPaths: ["apps/api/**", "packages/shared/**"]
      ignoredPaths: ["**/*.md"]
```

## What else happens on a push

- If the repo has a `stackblaze.yaml`, StackBlaze applies it at the pushed commit before rebuilding. See [Config as Code](/blueprint/).
- Several pushes close together collapse into one build of the newest commit.
- A new build for a service cancels that service's build that is still running.
- Your plan limits how many builds run at once in the workspace. There is no queue: a build over the limit is refused.
- Builds stop after the plan's build timeout (30 minutes unless your plan sets another value).

## Step by step

1. **Connect your GitHub repository**

   Add a service from **+ Service → GitHub repository**. Install the StackBlaze GitHub App on the repo or organization when asked. See [Deploy from GitHub](/deploy/github/).

2. **Pick the branch**

   In **Settings**, choose the **Branch**. Turn **Autodeploy** off if you only want manual deploys.

3. **Set build filters (optional)**

   For a monorepo, set the **Build path** in **Settings** (relative to the repo root). The service then only rebuilds for changes in that folder. Add `buildFilter` in `stackblaze.yaml` for shared folders or ignored files.

4. **Push a commit**

   Push to the branch. Add `[skip deploy]` to the message to push without deploying.

5. **Watch the deploy**

   Open the **Deployment** tab. Pick **Inspect Deployment** from a row's menu to see its build and rollout logs.

6. **Service goes live**

   When the new revision passes its health check, it takes the traffic. Earlier deploys stay in the list so you can [roll back](/cicd/rollbacks/) or **Redeploy** one.

## Deploy a specific commit

On the **Deployment** tab, choose a commit from the commit picker (search, or paste a SHA) and click **Deploy commit**.
