StackBlaze sends traffic to a new version of a web service only after its health check passes. If a running instance stops answering, it is restarted. Health checks are on by default.

Health checks apply to web services. They use one HTTP path that you set, and run three checks against it: **startup**, **readiness**, and **liveness**. A response with a 2xx or 3xx status passes.

## The three checks

### Startup

Runs when an instance starts, once per second, for up to the **Startup** time (default 90 seconds). Readiness and liveness wait until it passes. If it never passes, the instance is restarted. Raise it for services that boot slowly, such as JVM services or apps that load large models.

### Readiness

Decides whether the instance gets traffic. It runs every **Interval** seconds (default 10). An instance that keeps failing is taken out of traffic until it passes again. During a deploy, old instances keep serving until the new ones pass.

### Liveness

Catches a process that is stuck but has not crashed. It runs every 3 seconds. After 3 failures in a row, the instance is restarted.

Each request waits up to **Timeout** seconds (default 3) for an answer.

The checks send the service's first domain as the `Host` header, so apps that check the host name still answer. Services in sleep mode are not probed.

## Configure health checks

1. Open the service on the project canvas and go to **Settings → Health checks**.
2. Leave the switch **On**, or turn it **Off** if your service has no HTTP endpoint to probe. With health checks off, deploys are not gated.
3. Set **Path** (default `/`) to your health endpoint, for example `/health`.
4. Adjust **Startup**, **Timeout**, and **Interval** in seconds if needed.
5. Commit the staged changes.

Whether health checks start on or off comes from the environment's deploy defaults (on, unless the environment changes it). A service can override that, and **Reset** goes back to the environment default.

In `stackblaze.yaml`, set `healthCheckPath` on a service. That turns health checks on with a 30 second startup time, a 5 second timeout, and a 10 second interval.

## Health endpoint examples

### Node.js (Express)

```js title="server.js"
const express = require('express');
const app = express();

// Minimal health check, always returns 200
app.get('/health', (req, res) => {
  res.json({ status: 'ok', uptime: process.uptime() });
});

// Check the database before reporting ready
app.get('/health/ready', async (req, res) => {
  try {
    await db.query('SELECT 1');
    res.json({ status: 'ready', db: 'connected' });
  } catch {
    res.status(503).json({ status: 'unhealthy', db: 'disconnected' });
  }
});
```

### Python (FastAPI)

```python title="main.py"
from fastapi import FastAPI, HTTPException
from sqlalchemy import text

app = FastAPI()

@app.get("/health")
async def health_check():
    try:
        await db.execute(text("SELECT 1"))
        return {"status": "ok"}
    except Exception as e:
        raise HTTPException(status_code=503, detail=str(e))
```

:::caution
The same path is used for liveness. If it fails whenever the database is down, every instance is restarted during a database outage. Keep the liveness path cheap, or point it at a route that only checks the process itself.
:::

## Check health from an agent

The MCP tool `check_app_health` returns one verdict for a service (healthy, starting, degraded, crashlooping, and so on) with recent restarts and crash causes.
