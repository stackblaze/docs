---
title: Volumes
description: Attach a volume to a service so its files survive restarts and redeploys.
---

Files inside a container are ephemeral. A **volume** is a disk mounted into a service at a path you choose, so data written there survives restarts and redeploys. Use it for SQLite, uploads, model caches, and similar.

A volume you add in the dashboard is a shared filesystem: every instance of the service mounts the same volume and sees the same files. For data that other services must read too, use [object storage](/data-storage/) or a database on the canvas.

## Add a volume

1. Open the service on the project canvas and go to **Settings → Volumes**.
2. Click **Add volume**.
3. Set the fields:

   | Field | Example | Notes |
   | --- | --- | --- |
   | Name | `uploads` | Identifies the volume. |
   | Size | `5 GB` | Pick from 5 GB up to 1 TB. New volumes default to 5 GB. |
   | Mount path | `/data` | Absolute path inside the container. Each volume needs its own path. The first one defaults to `/data`. |

4. Review the staged changes and commit. The volume is mounted on the next deploy.

Once a volume is in use, its name and size are locked in the form. Pick a size with room to grow.

If **Volumes** shows an upgrade tag, your plan does not include volumes. Volumes you already have keep working and can still be removed.

## Remove a volume

Click **Remove** on the volume and commit the change. The service stops mounting it. The data is not deleted with it: the volume stays until it is deleted separately.

## Browse files

Services with a volume get a **Files** tab. From there you can browse folders, open and edit text files, upload and download files, create folders, and rename or delete entries. Your platform admin can turn the file browser off.

## Snapshots and backups

- **Backups**: volumes are included in the environment's recovery points when backups are turned on. See [Backups & recovery](/databases/backups/).
- **Snapshots**: the **Snapshots** tab takes a snapshot of all of a service's volumes (its own and its add-ons') at once. It only shows when the cluster supports volume snapshots. To get data back, clone the snapshot into a new service. A restore never overwrites a running volume.

## Billing

Volumes are billed on their provisioned size per GiB-month, not on what you use. An empty 10 GB volume is billed as 10 GB. See [Pricing](/reference/pricing/).

## Example: SQLite on a volume

```js title="app.js (Node.js)"
const Database = require('better-sqlite3');

// Path inside the volume's mount path
const db = new Database('/data/app.db');

db.exec(`
  CREATE TABLE IF NOT EXISTS users (
    id    INTEGER PRIMARY KEY,
    email TEXT UNIQUE NOT NULL
  )
`);
```

SQLite allows one writer at a time. If several instances share the volume, run one instance or move to a managed database.

## From the CLI

```bash
stackblaze volume list
stackblaze volume add uploads --mount /data/uploads --size 10Gi
stackblaze volume delete uploads

stackblaze files mounts
stackblaze files ls /data
stackblaze files upload ./seed.db --path /data/seed.db
stackblaze files download /data/uploads

stackblaze snapshots create
stackblaze snapshots list
```

`stackblaze volume add` defaults to `5Gi`. The `files` and `snapshots create` commands may be disabled by your platform admin.

## Config as code

In `stackblaze.yaml`, give a service a `disk` with `name`, `mountPath`, and `sizeGB` (default 1). A volume made this way attaches to one instance at a time, so the service is redeployed by stopping the old instance before the new one starts.

## MCP tools

- `snapshot_app`: snapshot all of an app's volumes under one group.
- `list_snapshots`: list an app's volumes and their snapshots.
- `clone_app`: restore a snapshot group into a new app, with new volumes and databases. The source is not touched.
- `get_snapshot_job`: check on a clone started by `clone_app`.
