---

Backups on StackBlaze work per environment. A **recovery point** holds the environment's services, its volumes, and a dump of each database. Backups are off until you turn them on. StackBlaze never creates a schedule for you.

## Opening Backup and restore

On the project canvas, open **+ Service → Backups**, or right-click a database and pick **Backups**. The **Backup and restore** sheet has two tabs: **Backups** and **Restore**.

## Turning on a schedule

On the **Backups** tab, the **Schedule** section has three cadences: **Daily**, **Weekly**, and **Monthly**. Tick the ones you want and pick how long to keep each (from 3 days to 1 year). Your plan caps the retention you can pick.

| Plan | Backup retention |
| --- | --- |
| Free Trial | Not included |
| Developer | 7 days |
| Pro | 14 days |
| Business | 30 days |

See [Plans](/reference/pricing/) for current plan details. If your workspace reaches its disk cap, scheduled backups pause and resume on their own once usage drops below the cap.

Saving a schedule also turns off the separate database dump schedule, because every recovery point already holds the databases.

## Backing up now

Click **Back up now** on the **Backups** tab, or **Back up `<name>`** when you opened the sheet from a database. This works without a schedule. The new point appears under **Recovery points**.

From the CLI:

```bash
stackblaze backups create --wait
stackblaze backups create --only web --only web-postgresql   # a partial point
```

## What a recovery point holds

| Engine | Held as |
| --- | --- |
| PostgreSQL, MariaDB, MySQL, MongoDB, FerretDB, Redis (official image) | A dump of the database |
| OpenSearch | A snapshot archive |
| ClickHouse | A native `BACKUP` archive |
| Valkey and other engines | A copy of the database's volume |
| Services | Their volumes |

## Restoring

Open the **Restore** tab, pick a recovery point under **From**, pick what to restore under **What**, and click **Stage restore**. Apply your staged changes to start it.

A restore always creates a **new** database (and a new volume) next to the running one, under a new name. Nothing running is interrupted or changed. Connect your services to the copy when you are ready, then delete the old one. Copies are billed like any other database or volume.

From the CLI:

```bash
stackblaze backups list
stackblaze backups restore latest --database web-postgresql --wait
```

## Deleted databases

When you delete a database, its dumps are kept. They show under **Deleted databases** on the **Restore** tab. Click **Restore as new database** to create a database from one of them, or delete the dumps when you no longer need them.

## Single-database dumps

For PostgreSQL and MariaDB you can also work with one database's dumps from the CLI. These commands never turn on a schedule.

```bash
stackblaze addons backups status web-postgresql   # is it covered by the schedule?
stackblaze addons backups create --wait           # dump now
stackblaze addons backups restore web-postgresql --backup <name> --wait
```

The restored database is named `<database>-restored`.

## Point-in-time recovery

For PostgreSQL you can also turn on [point-in-time recovery](/databases/pitr/). It archives the write-ahead log so you can restore to a chosen time, not only to a recovery point.

## Testing your backups

A backup you have never restored is not a backup. Restore a recovery point now and then, run your checks against the new database, then delete it.

```bash title="Example checks against the restored database"
#!/bin/bash
# Point DATABASE_URL at the restored database
export DATABASE_URL="postgres://user:pass@restored-db:5432/app"

psql "$DATABASE_URL" -c "SELECT COUNT(*) FROM users;"
psql "$DATABASE_URL" -c "SELECT COUNT(*) FROM orders WHERE created_at > NOW() - INTERVAL '7 days';"
```
