Managed PostgreSQL, run by the CloudNativePG operator. Versions 15, 16, and 17 are offered; new databases get PostgreSQL 17.

## Creating a PostgreSQL database

From **+ Service → Databases**, add **PostgreSQL**. It appears on the canvas as a staged change. Apply your staged changes and StackBlaze creates it with the catalog defaults: one instance and a 1 GB volume.

To connect a service, open the database, go to **Settings → Connection**, and switch the service on. You can also declare it in `stackblaze.yaml` under `databases` and reference it from a service with `fromDatabase`.

### TimescaleDB

**TimescaleDB** is a separate entry in the catalog. It is a PostgreSQL database on a TimescaleDB image, with the `timescaledb` extension created in the app database. Everything on this page applies to it. It is the Apache-2.0 edition, so compression, continuous aggregates, and hyperfunctions are not available. An existing database cannot be switched to or from TimescaleDB.

## Connection variables

A connected service gets these variables:

| Variable | Value |
| --- | --- |
| `PGHOST` | Internal hostname of the primary |
| `PGPORT` | `5432` |
| `PGUSER` | `postgres` |
| `PGPASSWORD` | Password, from a secret |
| `PGDATABASE` | `app` by default |
| `PGHOST_RO`, `PGPORT_RO` | Read-only endpoint (the replicas once HA is on) |
| `DATABASE_URL` | Only when the password is part of the database's definition, for example from a template or `stackblaze.yaml` |
| `PGHOST_POOLER`, `PGPORT_POOLER` | Only when the database includes a PgBouncer pooler (some templates add one) |

libpq-based clients (`psql`, `pg`, `psycopg`) read the `PG*` variables directly. If your app needs a URL and has no `DATABASE_URL`, compose one in its variables:

```text title="Variable"
DATABASE_URL=postgres://$(PGUSER):$(PGPASSWORD)@$(PGHOST):$(PGPORT)/$(PGDATABASE)
```

Build steps and the pre-deploy command get a `DATABASE_URL` built this way automatically when the service has the `PG*` variables but no usable `DATABASE_URL`.

### Internal

Services in the same environment talk over the private network. **Settings → Access** shows the host, user, password, database, connection URL (and JDBC URL), and an environment snippet you can paste into a service's variables.

```text title="Connection string (internal)"
postgres://postgres:password@[service-name]:5432/app
```

### From your machine

- `stackblaze connect postgres` opens `psql`. Add `--local` to run `psql` on your machine through a private tunnel, or `--tunnel` to keep a local port open for GUI tools such as TablePlus or DBeaver. The tunnel listens on `127.0.0.1` only.
- **Settings → Access → Public access** makes the database reachable from outside the platform, only from the IP addresses you allow. TLS is required. The CLI equivalent is `stackblaze addons expose <addon> --allow <ip/cidr>`.

## Running migrations

Run migrations as a pre-deploy command so they finish before the new version starts. Set it under **Settings → Deploy → Pre-deploy**. If the command fails, the current version stays live.

### Prisma

```bash title="Pre-deploy command"
npx prisma migrate deploy
```

### Node.js / npm script

```bash title="Pre-deploy command"
npm run migrate
```

### Django

```bash title="Pre-deploy command"
python manage.py migrate
```

There is no `stackblaze run` CLI. To load an existing dump, use `stackblaze addons import <file> [addon]` (plain SQL or `pg_dump` archives). It runs `psql` or `pg_restore` on your machine through a private tunnel.

## Backups and point-in-time recovery

Backups are off until you turn on a schedule for the environment. A recovery point holds a dump of each PostgreSQL database, and a restore always creates a new database next to the running one. See [Backups & recovery](/databases/backups/).

[Point-in-time recovery](/databases/pitr/) is available for PostgreSQL. You turn it on per database. It archives the write-ahead log, so you can restore the database as it was at a chosen time, into a new database.

## Extensions

**Settings → Extensions** lists the extensions available on the database's image and lets you enable them per database. Extensions marked **needs restart** load a library into `shared_preload_libraries`, which restarts the cluster.

You can also enable an extension in SQL:

```sql title="Enable an extension"
CREATE EXTENSION IF NOT EXISTS pg_trgm;
```

## High availability

Open the database, go to **Settings → HA**, and click **Enable HA**. The cluster grows to 3 instances with streaming replication and automatic failover. HA needs a plan with database high availability (Pro or Business). It is one-way: there is no in-place downgrade.

Send read-only traffic to `PGHOST_RO` to use the replicas. While the cluster has one instance, the read-only endpoint has no members.

## Connecting with common ORMs

### Prisma

```prisma title="prisma/schema.prisma"
datasource db {
  provider = "postgresql"
  url      = env("DATABASE_URL")
}
```

### Drizzle ORM

```ts title="db.ts"
import { drizzle } from 'drizzle-orm/postgres-js'
import postgres from 'postgres'

const client = postgres(process.env.DATABASE_URL!)
export const db = drizzle(client)
```

### SQLAlchemy (Python)

```python title="database.py"
import os
from sqlalchemy import create_engine

engine = create_engine(
    os.environ["DATABASE_URL"].replace("postgres://", "postgresql://", 1),
    pool_size=5,
    max_overflow=10,
    pool_pre_ping=True,
)
```
