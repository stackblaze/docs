An accidental `DROP TABLE` or a bad migration can damage data in seconds. Point-in-time recovery (PITR) lets you get the database back as it was just before, not only as it was at the last recovery point.

PITR is for PostgreSQL databases. It is off until you turn it on for a database. Today you turn it on and restore through the [REST API](/reference/api/); the dashboard and CLI work with [recovery points](/databases/backups/) only.

<Steps>

1. **Turn PITR on**

   PITR needs a plan that includes database backups and a region with a bucket store for the archive; the status call below says `available` and, if not, why. StackBlaze then archives the database's write-ahead log and takes a base backup every day at 02:00 UTC. Pick a retention of 7, 14, or 28 days; your plan caps it.

   ```bash
   curl -X PUT https://api.stackblaze.cloud/api/pipelines/{pipeline}/{phase}/backups/db/{database}/pitr \
     -H "Authorization: Bearer sb_pat_..." \
     -H "Content-Type: application/json" \
     -d '{"enabled": true, "retentionDays": 7}'
   ```

2. **Check the recovery window**

   `GET` the same path. The answer shows whether PITR is on, the retention, the WAL archiving health, the earliest and latest time you can restore to, and the restores you have started.

3. **Restore to a time**

   Pick a time inside the window, in UTC. Use deploy history or logs to narrow it down, for example five minutes before a bad migration ran.

   ```bash
   curl -X POST https://api.stackblaze.cloud/api/pipelines/{pipeline}/{phase}/backups/db/{database}/restore-pitr \
     -H "Authorization: Bearer sb_pat_..." \
     -H "Content-Type: application/json" \
     -d '{"targetTime": "2026-11-20T14:05:00Z"}'
   ```

   The restore always creates a **new** database. The original keeps running unchanged.

4. **Switch over**

   Connect a staging service to the new database first and run your checks. Then connect your production services to it and disconnect the old one.

</Steps>

To turn PITR off, send `{"enabled": false}`. The archive is kept until its retention runs out, then deleted.

:::caution
Writes made to the original database after the target time are not in the new database. If you need them, plan how to merge them before you switch over.
:::
