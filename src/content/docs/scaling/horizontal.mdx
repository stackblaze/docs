Run multiple instances (replicas) of your service to handle more traffic and improve availability. New instances become ready before they take traffic.

## Setting the instance count

Open the service → **Settings → Scale** and use **Instances** (− / +). A service with a worker process has a separate **Worker process** count. New instances come up, pass health checks, then take traffic. The section shows how many instances your plan allows ("Up to N on your plan").

Turn on **Autoscale** to set a min and max instead. See [Autoscaling](/scaling/autoscaling/).

In [`stackblaze.yaml`](/blueprint/), set `numInstances`.

## Instance limits by plan

| Plan | Max instances per service |
| --- | --- |
| Free Trial | 1 |
| Developer | 1 |
| Pro | 3 |
| Business | 10 |

A save above the limit is refused. Current values are on [Pricing](/reference/pricing/).

:::note
Your plan's **max size per service** (CPU and memory) is shared by all of the service's instances. More instances means a smaller share each. See [Memory & CPU limits](/scaling/limits/).
:::

## Traffic distribution

Requests are spread across healthy replicas. There is no sticky session by default — any replica may handle the next request. Keep services stateless (sessions in Redis, files in object storage).

## Designing for horizontal scaling

For horizontal scaling to work reliably, your service should be stateless. Here's what "stateless" means in practice:

- **Don't store user sessions in memory.** Use Redis or a database-backed session store so any replica can serve any request.
- **Don't store uploaded files on disk.** Use object storage (S3-compatible) so files are accessible from all replicas.
- **Don't use in-memory caches for shared state.** Each replica has its own memory. Use Redis for shared cache.
- **Use database-level locking for coordination.** If multiple replicas might process the same job, use advisory locks or atomic updates to prevent double-processing.

### Stateless session example

```ts title="server.ts"
import session from 'express-session'
import { createClient } from 'redis'
import { RedisStore } from 'connect-redis'

// Sessions stored in Redis, accessible from all replicas
const client = createClient({ url: process.env.REDIS_URL })
await client.connect()

app.use(session({
  store: new RedisStore({ client }),
  secret: process.env.SESSION_SECRET!,
  resave: false,
  saveUninitialized: false,
}))
```

## Zero-downtime scaling

When you add instances, new ones only get traffic after they pass their health check. When you remove instances, they get `SIGTERM` and a grace period to finish in-flight requests before they are stopped.

Scaling up or down does not cause request errors as long as your service shuts down gracefully.

### Graceful shutdown (Node.js)

```ts title="server.ts"
const server = app.listen(process.env.PORT || 8080)

process.on('SIGTERM', () => {
  console.log('SIGTERM received, draining connections')
  server.close(() => {
    console.log('Server closed')
    process.exit(0)
  })

  // Force exit if connections don't drain in time
  setTimeout(() => process.exit(0), 25_000)
})
```

:::tip
Always handle `SIGTERM`: stop accepting new connections, finish in-flight requests, then exit.
:::
