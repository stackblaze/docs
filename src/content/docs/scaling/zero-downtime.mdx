Deploys on StackBlaze are rolling updates. New instances become healthy before old ones stop, so your users do not see an outage.

## How rolling updates work

When you deploy, StackBlaze first builds the image and runs your pre-deploy command, if you set one. Then it starts new instances on the new version. Each new instance gets traffic only after it passes its health check; old instances are stopped after that.

The update continues instance by instance until all of them run the new version:

<Diagram file="zero-downtime-rolling.svg" alt="Timeline of rolling update replacing v1 pods with v2 pods one at a time" />

*New instances pass their health check before old ones stop, so traffic never drops to zero.*

1. The new image is built
2. The pre-deploy command runs in the new image (for example `npm run migrate`); if it fails, the deploy stops here
3. A new instance starts
4. StackBlaze probes the health check path until it answers
5. Traffic starts going to the new instance
6. An old instance gets `SIGTERM`, finishes in-flight requests, then exits

## When a deploy is not rolling

- **A volume that only one instance can mount** (ReadWriteOnce): the old instance stops before the new one starts, so expect a brief gap on each deploy. The **Deploy** section of the service settings warns about this.
- **Health checks turned off**: rollouts are not gated; new instances take traffic as soon as they start.

## Health checks

Health checks are on by default for services with a public or internal URL. Configure them under the service **Settings → Health checks**:

| Setting | Default for a new service | Meaning |
| --- | --- | --- |
| **Path** | `/` | HTTP path StackBlaze requests (`GET`) |
| **Startup** | 90 s | How long a new instance may take to start |
| **Timeout** | 3 s | Max wait for one response |
| **Interval** | 10 s | Time between probes |

Use a dedicated path such as `/health` that answers fast and returns 200 only when the app can serve real requests. Turn the switch off to deploy without a health gate. After you change it, **Reset** returns the service to the default.

In [`stackblaze.yaml`](/blueprint/), set `healthCheckPath`.

### Implementing a health endpoint

```js title="Node.js / Express"
// Fast health check, no DB query, just confirm the process is up
app.get('/health', (req, res) => {
  res.json({ status: 'ok', uptime: process.uptime() })
})

// Deeper readiness check, verify DB connection
app.get('/ready', async (req, res) => {
  try {
    await db.query('SELECT 1')
    res.json({ status: 'ready' })
  } catch (err) {
    res.status(503).json({ status: 'not ready', error: err.message })
  }
})
```

```python title="Python / FastAPI"
from fastapi import FastAPI, HTTPException

app = FastAPI()

@app.get("/health")
async def health():
    return {"status": "ok"}

@app.get("/ready")
async def ready():
    try:
        await db.execute("SELECT 1")
        return {"status": "ready"}
    except Exception as e:
        raise HTTPException(status_code=503, detail=str(e))
```

:::tip[Keep health checks fast]
The health check runs at its interval (10 seconds by default) while the service runs. If it makes slow queries or external HTTP calls, it can cause spurious "not ready" states. Keep health endpoints lightweight, check that your server is up, not that every dependency is working perfectly.
:::

## Pre-deploy commands and migrations

The most dangerous part of a deploy is running database migrations while the old code is still running. StackBlaze lets you define a pre-deploy command that runs in the freshly built image before the new version starts. This is the safest place to run migrations.

Set it in **Settings → Deploy → Pre-deploy**, or `preDeployCommand` in `stackblaze.yaml`. The image needs a shell.

### Writing safe migrations

Since both the old and new versions of your code may run simultaneously during a rolling update, migrations must be backward-compatible with the old code:

- **Adding a column**: safe. Old code ignores columns it doesn't know about (in most ORMs).
- **Dropping a column**: not safe in a single deploy. First deploy the code that stops using the column, then drop it in a separate migration deploy.
- **Renaming a column**: not safe. Add the new column, copy data, update code to use both, then remove the old column in a later deploy.
- **Adding a non-nullable column without a default**: not safe. Old code won't know to set it. Add with a default value first, then make it required later.

:::caution[Failed migrations block the deploy]
If your pre-deploy command exits with a non-zero code, the deploy stops and no instances are updated. Your current version keeps running unaffected. Always test migrations on a staging environment first.
:::

## Graceful shutdown

When an instance is stopped, its main process gets `SIGTERM`, then a grace period to finish in-flight requests before it is killed. Handle this signal to avoid dropping requests.

```ts title="Graceful shutdown (Node.js)"
import { createServer } from 'http'

const server = createServer(app)
server.listen(process.env.PORT || 8080)

let isShuttingDown = false

// Stop accepting new requests immediately
server.on('request', (req, res) => {
  if (isShuttingDown) {
    res.setHeader('Connection', 'close')
    res.status(503).json({ error: 'Server shutting down' })
  }
})

process.on('SIGTERM', () => {
  isShuttingDown = true
  console.log('SIGTERM received, closing server')

  server.close(() => {
    console.log('All connections closed, exiting')
    process.exit(0)
  })

  // Force exit if connections don't drain in time
  setTimeout(() => {
    console.log('Force exit after timeout')
    process.exit(0)
  }, 25_000)
})
```
