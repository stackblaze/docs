Autoscaling adds and removes instances of a service based on CPU or memory utilization, between a minimum and maximum you set.

<Diagram file="autoscaling.svg" alt="Chart showing traffic spike, replica count scaling up, and hourly spend cap line" />

## Enabling autoscaling

Open the service → **Settings → Scale** and turn on **Autoscale**. Set **Min** and **Max** instances (and the same for the **Worker process**, if the service has one). Under **Scale up when…**, pick the metrics.

The max cannot exceed your plan's instances per service (Pro: 3, Business: 10). On plans with one instance per service, autoscaling has no room to scale.

In [`stackblaze.yaml`](/blueprint/):

```yaml title="stackblaze.yaml"
services:
  - name: api
    scaling:
      minInstances: 2
      maxInstances: 6
      targetCPUPercent: 80
```

## Scaling metrics

| Metric | Default | Range |
| --- | --- | --- |
| **CPU** above N% average utilization | On, 80% | 10–90% |
| **Memory** above N% average utilization | Off (80% when turned on) | 10–90% |

Utilization is a percentage of the instance's resources. When neither metric is on, the service does not autoscale.

:::caution[Memory autoscaling caveat]
Memory is not released as quickly as CPU. Some runtimes (especially JVM-based apps and Node.js) hold on to their heap, so a service that scales up on memory may never scale back down. That is why memory is off by default.
:::

## Min and max instances

- **Min**: the floor. The service never runs fewer instances, even with no traffic. Use 2 or more for high availability.
- **Max**: the ceiling. It protects against runaway scaling from a traffic spike or a bug. Pick a value your database connections and your budget can handle.

:::note
Your plan's max size per service is split across the instances the service can run, counting an autoscaled service at its **Max**. A higher max therefore means a smaller CPU and memory share per instance. See [Memory & CPU limits](/scaling/limits/).
:::

## Autoscaling and databases

When your service scales up, each new instance opens its own database connections. Size your connection pool for the maximum instance count:

```ts title="Database connection pool configuration"
// Each instance opens up to 10 connections
// With max 5 instances, the database receives up to 50 connections
import { Pool } from 'pg'

const pool = new Pool({
  connectionString: process.env.DATABASE_URL,
  max: 10,            // connections per instance
  idleTimeoutMillis: 30_000,
  connectionTimeoutMillis: 5_000,
})
```

Your plan also caps database connections; see [Pricing](/reference/pricing/).

## Monitoring autoscaling

Use the service's **Metrics** tab to see CPU and memory over the last 2 hours, 24 hours, or 7 days.
