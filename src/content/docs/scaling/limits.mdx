## Where the limits come from

There are no server sizes to pick. Each plan has a **max size per service**, and StackBlaze sets every service's CPU and memory limits from it:

| Plan | Max size per service |
| --- | --- |
| Free Trial | 0.5 vCPU · 0.5 GB |
| Developer | 2 vCPU · 4 GB |
| Pro | 4 vCPU · 16 GB |
| Business | 8 vCPU · 32 GB |

Current values are on [Pricing](/reference/pricing/).

That size is shared by all of the service's instances: web and worker instances, with an autoscaled service counted at its **Max**. One instance gets the full size; two instances get half each. Helper containers in the same instance (for example the App Shield WAF) count inside that share, and your app always keeps at least 60% of it. Each scheduled-task run gets the same share as one instance.

To give each instance more CPU and memory, run fewer instances, or move to a larger plan. After an upgrade, a running service picks up the new size on its next save, deploy, or restart.

## At the CPU cap

When an instance hits its CPU limit, it is **throttled**. The process keeps running, but it gets less CPU time, so request latency goes up and background work slows down. Throttling is not a crash.

If **Metrics** shows CPU sitting at the limit for a long stretch:

- Reduce the instance count, so each instance gets a larger share, or upgrade the plan
- Or optimize the hot path

## At the memory cap

When an instance hits its memory limit, the process is **OOM-killed** and restarted. Unlike CPU, memory is not throttled; there is no graceful slowdown.

Check **Metrics** for memory. If it climbs to the limit and the instance restarts:

- Shrink in-process caches
- For Node.js, pass `--max-old-space-size` **below** the container memory limit so V8 collects garbage before the process is killed
- Reduce the instance count or upgrade the plan for a larger share

Open [Coroot](/operations/observability/) from the service (**Open in Coroot** on the Metrics tab) to confirm OOMs and see CPU and memory over time.

## Diagnose from the dashboard

1. Open the service → **Metrics** and look at CPU and memory over 2 hours, 24 hours, or 7 days.
2. If CPU is flat at the limit and latency is high, the service is throttled.
3. If memory hits the limit and the instance restarts, it was OOM-killed. Check **Logs** around the restart.
4. Change the instance count under **Settings → Scale**, or upgrade the plan.
