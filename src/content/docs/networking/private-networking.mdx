Services in the same **environment** talk over a private network using stable internal hostnames. Traffic never goes over the public internet.

## How it works

Each environment (production, a custom environment, a PR preview) has its own private network. Every service and database in it gets a stable internal hostname that only resolves and connects inside that environment. Traffic between services never leaves the cluster.

*Public traffic hits your web service; app-to-database traffic uses internal service hostnames on the private network.*

## Internal hostnames

Do not hardcode internal hostnames. Use variables instead:

- **Reference another service's variables** with `${{service.VAR}}`. Every service has a virtual `STACKBLAZE_PRIVATE_DOMAIN`: its internal hostname. The reference resolves inside the current environment, so a PR preview or staging copy automatically points at its own services.
- **Databases** inject their connection variables (host, port, user, password, connection string) when you connect them to a service. In `stackblaze.yaml`, use `fromDatabase`.

```text title="Variables on the api service"
WORKER_URL=http://${{worker.STACKBLAZE_PRIVATE_DOMAIN}}:3000
API_KEY=${{worker.API_KEY}}
```

Other virtual variables you can reference: `STACKBLAZE_PUBLIC_URL` (`https://` plus the first public hostname) and `STACKBLAZE_PUBLIC_DOMAIN`.

A service's full internal hostname has the form `<service>-kuberoapp.<project>-<environment>.svc.cluster.local`. StackBlaze also adds a short alias with the plain service name, so `http://worker:3000` works too (handy for Compose-style configs). Database add-ons get an alias with their name as well, such as `db` or `redis`, unless another service already uses it.

## Ports

Connect to the port the service or database listens on:

- Services: the port in the service settings
- PostgreSQL: `5432`
- MySQL / MariaDB: `3306`
- Valkey / Redis: `6379`

Services with **Internal** access serve HTTP on the private network only, with no public URL. **Worker** services have no HTTP port.

## Service-to-service communication

Internal requests don't go through the public edge; they travel directly between services over the cluster network. This means:

- Lower latency (typically under 1ms within a region)
- No TLS overhead required (traffic is private to the cluster)
- No firewall rules to configure

### Example: API calling an internal worker

```ts title="api/src/jobs.ts"
// Call a background worker service over the internal network
const response = await fetch(`${process.env.WORKER_URL}/process`, {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ jobId: '123', payload: data }),
})

const result = await response.json()
```

## Authentication on the internal network

Internal network access is not authenticated by default: any service in the same environment can reach any other service by its internal hostname. If your services handle sensitive data, implement application-level authentication using a shared secret environment variable or mTLS.

```js title="Simple shared secret auth"
// In your worker service, verify caller is legitimate
app.use('/internal', (req, res, next) => {
  const secret = req.headers['x-internal-secret']
  if (secret !== process.env.INTERNAL_API_SECRET) {
    return res.status(403).json({ error: 'Forbidden' })
  }
  next()
})
```

:::tip
Add `INTERNAL_API_SECRET` as a shared environment variable to both the calling service and the worker. Rotate it from the dashboard when needed.
:::

## Cross-project communication

The private network is scoped to one environment of one project. Services in another environment or another project cannot reach it by internal hostname.

To talk across projects, call the other service's public URL and secure it with an API key or token.

:::caution[Don't use public URLs for database connections]
Databases have no public URL by default. Use the injected connection variables from inside the environment.
:::
