Managed RabbitMQ: an AMQP message broker as a single node or a three-node high-availability cluster, with a management UI.

## Creating a RabbitMQ instance

On the project canvas, open **+ Service → Add-ons** and pick **RabbitMQ**. RabbitMQ sits under Add-ons, not Databases. A new instance runs one node with a 1 GiB volume.

RabbitMQ is a message broker rather than a traditional database. Instead of storing rows you query, it moves messages between producers and consumers through **queues** and **exchanges** over the AMQP protocol. This makes it a good fit for background jobs, work distribution, and service-to-service messaging where you want to decouple the sender from the receiver.

Connect RabbitMQ to a service and these variables are injected, so your app reads them from the environment instead of hardcoding credentials:

| Variable | Value |
| --- | --- |
| `RABBITMQ_HOST` | `[service-name]` |
| `RABBITMQ_PORT` | `5672` |
| `RABBITMQ_USERNAME` | The default user (`guest` unless you changed it) |
| `RABBITMQ_PASSWORD` | The default user's password, from a secret |
| `RABBITMQ_URL`, `AMQP_URL` | `amqp://user:password@[service-name]:5672/`, set when the password is known at creation |

If `RABBITMQ_URL` is not set on your service, build the URL from the four variables above.

## Connecting

RabbitMQ speaks **AMQP 0-9-1** on port `5672`. The URL contains the username, password, internal hostname, and port your client needs.

```text title="RABBITMQ_URL"
amqp://user:password@[service-name]:5672/
```

Most AMQP client libraries accept this URL directly. The internal hostname resolves only inside the environment's private network. AMQP is not reachable from outside.

## Management UI

The RabbitMQ management UI (port `15672`) shows queues, exchanges, connections, and message rates. Open the RabbitMQ service and go to **Settings → Access** for its in-cluster URL and the default user's credentials. You can also turn on a **Public** HTTPS address for the management UI there, or with `stackblaze addons expose`. Only the management UI is exposed, not AMQP.

In the chat assistant, RabbitMQ admin tools appear with the `rmq__` prefix.

## Standard vs high availability

<Diagram file="rabbitmq-standard-vs-ha.svg" alt="Standard RabbitMQ is a single node. High availability is a multi-node cluster that replicates messages with quorum queues." />

Every instance starts as Standard. To move to high availability, open the RabbitMQ service, go to **Settings → HA**, and click **Enable HA**.

**Standard** runs a single node. It is simple and a good fit for development, staging, and workloads that can tolerate a brief interruption. If that node is lost, the broker is unavailable until it restarts.

**High availability** runs a three-node cluster. To keep messages when a node is lost, declare your queues as **quorum queues** (`x-queue-type: quorum`), which replicate each message across nodes. Classic queues live on one node.

| | Standard | High availability |
| --- | --- | --- |
| Nodes | 1 | 3 |
| Queue replication | None | Quorum queues replicate across nodes |
| Tolerates node loss | No | Yes, for quorum queues |

:::caution[One-way change]
Enabling HA cannot be undone in place. To go back to a single node, create a new RabbitMQ instance. Database high availability is included on the Pro and Business plans.
:::

## Publishing and consuming

The example below uses `amqplib` in Node.js. It reads the connection string from `process.env.RABBITMQ_URL`, asserts a durable queue, publishes a message, and consumes it.

```js title="worker.js"
const amqp = require('amqplib')

async function main() {
  const conn = await amqp.connect(process.env.RABBITMQ_URL)
  const channel = await conn.createChannel()

  const queue = 'jobs'
  await channel.assertQueue(queue, { durable: true })

  // Publish a message
  channel.sendToQueue(queue, Buffer.from('hello'), { persistent: true })

  // Consume messages
  await channel.consume(queue, (msg) => {
    if (msg) {
      console.log('received:', msg.content.toString())
      channel.ack(msg)
    }
  })
}

main().catch(console.error)
```

## Backups

RabbitMQ definitions (queues, exchanges, bindings, and users) and persistent messages live on a persistent volume. Backups are off until you turn them on for the environment. When they are on, recovery points include that volume. See [Backups & recovery](/databases/backups/).

:::note[Under the hood]
RabbitMQ runs via the RabbitMQ Cluster Operator, with a **persistent volume per node** for definitions and message storage. In HA, quorum queues replicate messages across the three nodes, so losing one node does not lose those messages or take the broker offline.
:::
