From **+ Service → Import**, drop a Compose file, `render.yaml`, or `fly.toml` onto the canvas. Application containers become **services**. Databases and caches become **managed databases** on the same board, with backups and private networking.

<Diagram file="compose-to-canvas.svg" alt="Compose web, postgres, and redis map onto the canvas as a web service plus managed PostgreSQL and Redis, not DIY datastore containers." />

The mapping is usually mechanical. The Compose example below is the common case; Render and Fly imports follow the same canvas result.

## Example `docker-compose.yml`

```yaml title="docker-compose.yml"
version: "3.9"

services:
  web:
    build: .
    ports: ["3000:3000"]
    environment:
      - DATABASE_URL=postgres://postgres:secret@postgres:5432/app
      - REDIS_URL=redis://redis:6379
    depends_on: [postgres, redis]

  postgres:
    image: postgres:16-alpine
    environment:
      POSTGRES_PASSWORD: secret
      POSTGRES_DB: app
    volumes:
      - pgdata:/var/lib/postgresql/data

  redis:
    image: redis:7-alpine
    volumes:
      - redisdata:/data

volumes:
  pgdata:
  redisdata:
```

## What you end up with

| Kind | Name | On the canvas |
| --- | --- | --- |
| service | `web` | Built from your Dockerfile, port 3000 |
| database | `postgres` | Managed PostgreSQL |
| database | `redis` | Managed Valkey (Redis-compatible) |

`DATABASE_URL` and `REDIS_URL` point at Compose service names, so import rewrites them to the managed databases' connection strings. The `pgdata` and `redisdata` volumes are not needed: database storage is managed. `depends_on` is ignored.

Import stages the tiles. **Commit N changes** → **Deploy** applies them ([staged changes](/deploy/staged-changes/)). You can also describe the same stack in [config as code](/blueprint/).

## Compose → StackBlaze

| Compose key | StackBlaze equivalent |
| --- | --- |
| `build: .` | Service (from Dockerfile) |
| `image: postgres:16` | Managed PostgreSQL |
| `image: mariadb`, `mysql` | Managed MariaDB / MySQL |
| `image: redis:7-alpine`, `valkey` | Managed Valkey |
| `image: kafka` | Managed Kafka |
| `ports:` | Service port (first port); no ports makes a private worker |
| `command:` | Start command |
| `volumes:` (named) | Volume on that service |
| `environment:` | [Variables](/security/env-vars/) |
| `deploy.replicas` | Instance count |

## Under the hood

The mapping is consistent:

- **build / image**: source builds and your own images become **services**, same port and start command.
- **known datastores**: stock `postgres`, `mariadb`, `mysql`, `redis`/`valkey`, and `kafka` images become **managed databases**. Other datastores (for example `mongo`, `rabbitmq`, `elasticsearch`, `minio`) are skipped with a warning; add them from **+ Service → Database or cache** if available.
- **volumes**: the first named volume on a service becomes a **volume** at the same path. Bind mounts such as `./src:/app` are dropped.
- **environment**: values become [variables](/security/env-vars/). A value that points at a Compose datastore (a URL with its host, or just the host) is rewritten to that managed database. A value with `${VAR}` becomes a variable you must fill in.
- **ignored**: `depends_on`, `healthcheck` (set an HTTP health check path afterwards), `build.args`, and extra ports beyond the first.
- **networking**: other services are reachable by name on the environment's [private network](/networking/private-networking/).

## Step by step

<Steps>

1. **Keep your docker-compose.yml as the reference**

   Your Compose file is the checklist. Import it, then deploy the staged canvas.

2. **App containers become services**

   Anything you `build` or ship as your own image becomes a service from that Dockerfile or image, same port and command.

3. **Datastore containers become managed databases**

   Do not run your own postgres or redis container. Import maps those images to managed databases.

4. **Wire them together**

   Connection strings land as variables. Other services are reachable by name on the private network. `depends_on` is ignored: services start independently and retry.

</Steps>
