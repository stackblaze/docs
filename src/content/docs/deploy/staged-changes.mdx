Edits on the project canvas are **staged** until you deploy. Adding a service, attaching a database, changing variables, or removing a tile does not touch the running environment until you confirm.

<Diagram file="staged-changes.svg" alt="Canvas edits become a staged changeset, then you review and either deploy or discard" />

This is the same idea as a reviewable changeset: you compose, then apply.

## What gets staged

- New services (Git, Docker, template, import)
- New databases and add-ons
- Connections between services and databases
- Config changes on an existing service (variables, settings)
- Removals (shown as a delete preview on the canvas)

Staged tiles render on the canvas so you can see the topology before it exists.

## Deploy

When something is staged, the canvas toolbar shows **Commit N changes**. Click it (or press Enter) to open the review:

1. The dialog lists each staged change for the environment you are viewing. Click a row's unstage button to drop just that change.
2. Optionally type a **Commit message**: how these releases appear in the history.
3. Click **Deploy N changes**. If every change is a removal, the button reads **Delete N resources** and asks you to type a confirmation word first.

StackBlaze applies the changeset: it creates services, provisions databases, and rolls out config. Anything that fails stays staged so you can fix it and try again.

If a build fails, the running service stays on its previous deploy.

## Discard

**Discard all** in the review dialog drops the staged changeset. Live services are untouched.

## After deploy

Watch build and deploy logs on the service's **Deployment** tab. Further git pushes [auto-deploy](/cicd/auto-deploy/) without staging anything.

## Config as code

`POST /api/iac/blueprint/compile` stages services from a `stackblaze.yaml` file onto the canvas. You still deploy from the dashboard to apply. [Config as Code](/blueprint/) `apply` upserts without deleting.
