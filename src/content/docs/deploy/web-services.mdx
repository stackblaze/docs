A service is public HTTP when its access is **Public**. StackBlaze gives it a URL, terminates TLS, load-balances, health-checks, and rolls out new revisions, without a separate “web service” product.

## Public HTTP on a service

In the service **Settings → Access**, pick one of:

- **Public** — public URL using the service's port.
- **Internal** — HTTP service reachable only inside the project; no public URL or domain.
- **Worker** — background process; no HTTP port, no domain. See [Private services](/deploy/background-workers/).

A public service gets a default `https://<service>-<suffix>.stackblaze.app` URL on its first deploy. Attach your own hostname with a [custom domain](/networking/custom-domains/).

HTTP/1.1, HTTP/2, and WebSockets work without extra config. Do not terminate TLS in the container — the platform forwards HTTP to it.

## Port

Each service has one HTTP port, set in the service settings. The repo scan or the framework preset fills it in (for example `3000` for Node.js, `8000` for FastAPI or Django, `8080` for Go). StackBlaze sets the `PORT` variable to that port. Bind to `0.0.0.0` (not `127.0.0.1`) so the process can receive traffic.

```javascript title="server.js"
// Node.js example
const port = process.env.PORT || 8080
app.listen(port, '0.0.0.0', () => {
  console.log(`Listening on port ${port}`)
})
```

```python title="main.py"
# Python / Gunicorn example
# StackBlaze sets PORT automatically
# gunicorn reads $PORT via --bind flag
# Procfile: web: gunicorn app:app --bind 0.0.0.0:$PORT
```

:::caution
Do not hardcode a port number. Read `process.env.PORT` (Node.js) or `os.environ["PORT"]` (Python), so the service keeps working if you change its port.
:::

## Health checks

A new instance gets traffic only after it passes its health check. Health checks are on by default for public and internal services.

Set them under **Settings → Health checks**:

| Setting | Default for a new service | Meaning |
| --- | --- | --- |
| **Path** | `/` | HTTP path StackBlaze requests (`GET`) |
| **Startup** | 90 s | How long a new instance may take to start |
| **Timeout** | 3 s | Max wait for one response |
| **Interval** | 10 s | Time between probes |

A dedicated endpoint such as `/health` is recommended. It should answer quickly without expensive database queries.

```javascript title="server.js"
// Recommended: lightweight health endpoint
app.get('/health', (req, res) => {
  res.json({ status: 'ok', uptime: process.uptime() })
})
```

Turning health checks off means rollouts are not gated. See [Zero-downtime deploys](/scaling/zero-downtime/).

## Start command

Set the **Start command** under **Settings → Deploy** (blank uses the framework default, or the image's default process for a Docker image service). It is what StackBlaze runs to start your application. It should start your HTTP server and block (not exit). If it exits, the platform considers the instance failed and restarts it.

| Runtime | Typical start command |
| --- | --- |
| Node.js | `node dist/server.js` |
| Node.js (npm) | `npm start` |
| Python | `gunicorn app:app --bind 0.0.0.0:$PORT` |
| Python (FastAPI) | `uvicorn main:app --host 0.0.0.0 --port $PORT` |
| Ruby | `bundle exec puma -C config/puma.rb` |
| Go | `./bin/server` |
| Java | `java -jar target/app.jar` |

## Scaling

Set the instance count under **Settings → Scale**, or turn on **Autoscale** with a min, a max, and a CPU or memory target (CPU at 80% by default). Your plan sets the maximum instances per service.

See [Horizontal scaling](/scaling/horizontal/) and [Autoscaling](/scaling/autoscaling/).

## Zero-downtime rolling updates

Every deploy is a rolling update: new instances start and must pass their health check before old ones stop. A service with a volume that only one instance can mount stops the old instance first, so expect a brief gap.

:::tip
For database migrations, set a **Pre-deploy** command under **Settings → Deploy** (for example `npm run migrate`). It runs in the new image before the new version starts; if it fails, the current version keeps running.
:::

## Node.js example

```javascript title="server.js"
import express from 'express'

const app = express()
const port = parseInt(process.env.PORT || '8080', 10)

app.use(express.json())

app.get('/health', (req, res) => {
  res.json({ status: 'ok' })
})

app.get('/', (req, res) => {
  res.json({ message: 'Hello from StackBlaze!' })
})

app.listen(port, '0.0.0.0', () => {
  console.log(`Server listening on port ${port}`)
})
```

## Python example

```python title="main.py"
from fastapi import FastAPI
import os

app = FastAPI()

@app.get("/health")
def health():
    return {"status": "ok"}

@app.get("/")
def root():
    return {"message": "Hello from StackBlaze!"}

# Start with: uvicorn main:app --host 0.0.0.0 --port $PORT
```

## Environment variables

StackBlaze sets these variables on a service:

| Variable | Description |
| --- | --- |
| `PORT` | The port your service should listen on |
| `STACKBLAZE_PUBLIC_URL` | `https://` plus the service's first public hostname |
| `STACKBLAZE_PUBLIC_DOMAIN` | The service's first public hostname |
| `STACKBLAZE_PREVIEW` | `true` in a [PR preview](/cicd/pr-previews/) |
| `STACKBLAZE_PR_NUMBER`, `STACKBLAZE_PR_BRANCH` | The pull request, in a PR preview |

Read more about variables in [Security → Environment Variables](/security/env-vars/).
