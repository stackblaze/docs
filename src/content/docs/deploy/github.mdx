---
title: Deploy from GitHub
description: Connect a repo on the canvas and deploy on every push.
---

From **+ Service → GitHub repository**, connect GitHub and pick a repo. Pushes to the connected branch [auto-deploy](/cicd/auto-deploy/). Pull requests can get their own [preview environment](/cicd/pr-previews/).

## Connect GitHub

The first time you add a Git service, StackBlaze asks you to install the **StackBlaze GitHub App** on your account or organization. On GitHub you can grant all repositories or only the ones you select.

Access is tied to the app installation, not to a personal token. StackBlaze clones with short-lived installation tokens. It does not add a webhook or a deploy key to each repository: the GitHub App receives push and pull request events for every repo it is installed on.

You can also paste the URL of a **public** Git repository instead of picking one from GitHub.

## Repository access

To give StackBlaze more repositories, use **Add GitHub org or repositories** in the repository picker, or change the app's repository access on GitHub (your account or organization settings → GitHub Apps → StackBlaze → Configure).

## Pick the repo, branch, and build

After you pick a repo, StackBlaze scans it and pre-fills:

- **Branch** — the branch to deploy. StackBlaze deploys its latest commit.
- **Build method** — **Docker** when it finds a Dockerfile, otherwise **Railpack** (auto-detect). **Buildpacks** and framework presets are also listed.
- **Build path** — the folder to build, relative to the repo root. In a [monorepo](/cicd/monorepo/), StackBlaze offers one service per app folder it finds.
- **Port**, **start command**, and health check path when it can detect them.

Change any of these later in the service **Settings**. Changing the branch deploys the latest commit of the new branch.

## Auto-deploy on push

When you push to the configured branch, the GitHub App notifies StackBlaze, which builds and deploys the new commit. Turn **Autodeploy** off in **Settings** for manual deploys only.

To skip one push, put `[skip deploy]`, `[deploy skip]`, `[skip cd]`, or `[cd skip]` in the commit message. `[skip ci]` does not skip a deploy.

## Build filters for monorepos

A service with a build path such as `packages/api` only rebuilds when files under that folder change. To also watch shared code, or to ignore some files, set `buildFilter` in [`stackblaze.yaml`](/blueprint/):

```yaml title="stackblaze.yaml"
services:
  - name: api
    rootDir: packages/api
    buildFilter:
      includedPaths: ["packages/api/**", "packages/shared/**", "packages/types/**"]
      ignoredPaths: ["**/*.md"]
```

:::tip
Include your shared packages, otherwise changes to shared code won't rebuild the services that depend on it.
:::

See [Auto Deploy on Push](/cicd/auto-deploy/#build-filters) for the full rules.

## Pull-request environments

When preview environments are on for the project, opening a pull request against the deploy branch creates a `pr-<number>` [preview environment](/cicd/pr-previews/). It updates on every push to the PR branch. StackBlaze posts one comment on the PR with the preview URLs and updates it as builds finish. Previews are deleted when the PR is merged or closed.

Pull requests from forks do not get previews.

## Build checks on GitHub

While a build runs, StackBlaze posts a check run named `Stackblaze / <build method>` on the commit. It finishes as success, failure, or timed out. You can use it in GitHub branch protection.

## Revoking access

Remove the repository from the StackBlaze GitHub App's repository access on GitHub, or uninstall the app.

This does not delete the service from StackBlaze; it stops receiving pushes and cannot clone the repo for new builds.
